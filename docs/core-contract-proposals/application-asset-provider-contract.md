# Core Application Asset Provider Contract Proposal

Status: Proposed upstream contract; not implemented in Core or Integration.

Date: 2026-08-20

## Objective

Allow Rust application consumers to use the exact Core rules and policy assets without requiring callers to know developer checkout paths, copying Core assets into Integration repositories, or maintaining a second governance source of truth.

The provider should be Core-owned and usable by `run_explainable_scan` and related application APIs.

## Proposed Public Boundary

The preferred design is an opaque Core-owned provider rather than exposing private parser types or requiring Integration to pass paths:

```rust
pub const CORE_ASSET_CONTRACT: &str = "core-assets-v1";

pub struct ApplicationScanRequest {
    pub category: Option<String>,
    pub persist_snapshot: SnapshotPersistence,
}

pub struct CoreAssetProvenance {
    pub contract: String,
    pub core_version: String,
    pub core_revision: Option<String>,
    pub source: String,
    pub rules_digest: String,
    pub policy_digest: String,
}

pub fn run_explainable_scan_with_default_assets(
    request: ApplicationScanRequest,
) -> Result<ExplainableScanResult>;
```

An equivalent API may expose a public `DefaultAssetProvider` and an application request builder. The important property is that Core resolves and loads the assets internally; Integration does not receive or recreate a second rules/policy implementation.

If callers need explicit test fixtures, Core may retain a separate test-only or trusted application API that accepts paths. The default production API must not require those paths.

## Rules Resolution

The provider must:

- resolve the exact rules set belonging to the running Core package;
- preserve rule schema version, source path or logical source, and digest provenance;
- use the same platform selection and path expansion as the Core CLI;
- fail closed if the rules asset set is missing, malformed, or incompatible;
- avoid current-working-directory and developer-manifest fallback in packaged production binaries;
- expose the resolved rules digest or complete asset manifest in result provenance.

The provider must not let Integration substitute its own `rules/` directory as a fallback.

## Policy Resolution

The provider must:

- resolve the policy shipped with the exact Core package or embedded Core asset set;
- preserve the policy snapshot used by scanner/planner semantics;
- expose a policy digest or asset manifest in provenance;
- apply the same default policy fallback semantics as the Core CLI only when explicitly documented by the contract;
- fail closed on missing or incompatible packaged policy rather than silently using a developer-machine path.

## Packaging Behavior

Core must select and document one supported packaging model:

1. runtime-adjacent assets shipped by the Core release, with a stable locator API; or
2. assets embedded/generated by Core's own build and exposed through the provider; or
3. a Core-provided package asset API that abstracts both models.

The Integration release must not store a maintained copy of Core rules or `config/policy.yaml`. If a Rust MCP binary embeds assets, the build must derive them from the exact pinned Core package/revision and record that provenance in generated metadata. Hand-authored copied assets are not acceptable.

## Version Compatibility

The provider must report:

```json
{
  "contract": "core-assets-v1",
  "core_version": "1.7.0",
  "core_revision": null,
  "source": "package-adjacent",
  "rules_digest": "sha256:...",
  "policy_digest": "sha256:..."
}
```

Compatibility rules:

- the asset provider contract identifier and version are required;
- assets must be compatible with the running Core application API;
- a mismatched or unknown asset contract is an error, not a warning;
- asset updates are tied to Core release/update semantics, not independently upgraded by Integration;
- exact runtime revision is optional only when Core cannot prove it, and must be marked unverified.

## Cross-Platform Behavior

The provider must be tested on Windows, macOS, and Linux and must:

- use platform-native path handling internally;
- avoid hardcoded developer paths;
- resolve assets relative to a documented package/binary location or embedded provider;
- handle spaces and Unicode paths;
- produce consistent rule/policy digests for the same asset bytes;
- return structured unavailable/incompatible errors when assets cannot be resolved.

## Safety Boundary

Asset resolution is read-only. The provider must not:

- download arbitrary assets;
- fetch a remote rules repository implicitly;
- write caches during strict diagnostic execution;
- alter rules or policy based on model input;
- bypass Core policy or risk semantics.

## Acceptance Tests For Core

Core should add application-boundary tests proving:

- default provider resolves packaged assets without caller paths;
- rules and policy digests are reported;
- missing/mismatched assets fail closed;
- adjacent and embedded packaging models behave consistently;
- Windows/macOS/Linux path behavior;
- `SnapshotPersistence::Skip` remains write-free;
- explainability results retain Core rule provenance and accounting semantics.
